## 1. Executive Summary

NX-COLLAB-1 backend/realtime/files foundation is already Live, but the current Browser Acceptance exposed a UI architecture mismatch: the Client Project experience is still rendered inside the legacy narrow Admin detail drawer, which compresses Tickets and Files and hides important workspace modules such as Client Access.

R4 will not patch the narrow drawer. It will introduce a dedicated **Client Project Workspace** that occupies the usable application viewport and uses the approved NEXORA visual language: dark futuristic surfaces, cyan/blue accents, high information clarity, restrained glow, compact project identity, and local-scroll work areas.

The R4 correction is a **frontend/UI architecture release only**. Existing D1 schema, migration `0010`, Durable Object realtime, R2 storage, Ticket business rules, portal grants, permissions, and current API contracts are protected unless an implementation review proves a minimal API additive change is strictly required.

## 2. Evidence / Current-State Findings

### 2.1 Admin workspace is constrained by the legacy drawer

Current Admin project details are opened through the generic `detail-drawer`, whose effective width is about 680–790px. That component was suitable for record details/forms, not for a multi-module collaboration workspace.

Observed consequences:

- Tickets list + conversation become cramped.
- Module navigation overflows horizontally.
- `Client Access` can be outside the immediately visible area.
- Files preview dominates the limited width and looks oversized.
- Project identity and progress lose the hierarchy shown in the approved reference.
- Browser viewport is mostly covered by a blurred backdrop while the actual workspace uses only a minority of the screen.

### 2.2 Client Access exists functionally but is not discoverable

The Admin source already contains the required grant workflow:

- Generate tracking link.
- Choose client contact.
- Configure allowed client permissions.
- Configure expiry.
- Copy generated portal URL.
- Revoke active links.

The problem is placement/discoverability, not absence of the backend capability.

### 2.3 Client Portal exposes an Admin-only concept

The current Client Portal includes a `Client Access / وصول العميل` tab. This is conceptually wrong. Access-grant management belongs only to Admin. A client should not see token/grant-management concepts or a permissions summary presented as an access-management module.

### 2.4 Files UI is viewer-first instead of workspace-first

The current Admin Files area makes the selected image consume most of the narrow drawer. R4 needs a file-management layout with hierarchy first, preview second.

## 3. R4 Product Decision

### 3.1 Admin Client Project becomes a dedicated workspace

Opening a Client Project will no longer use the standard narrow record drawer.

It will open a dedicated **Project Workspace Layer** inside the Admin application:

- Fixed/inset to the usable viewport.
- Preserves Admin global navigation context.
- Does not destroy the underlying Admin route/state.
- Has its own compact close/back action.
- No full-page body scrolling for normal workspace use.
- Each module manages its own intrinsic scrolling.

### 3.2 Client Portal remains a separate client product surface

The Client Portal will share the NEXORA design system but will not mirror Admin density or Admin-only controls.

Client navigation will contain only safe client-facing modules:

1. Project Overview / بيانات المشروع
2. Execution / تنفيذ المشروع
3. Tickets & Support / التذاكر والدعم
4. Files / الملفات — only client-visible files, if exposed by current permissions/runtime

**Client Access / وصول العميل is prohibited from the Client Portal.**

## 4. Approved Visual Direction

R4 must follow the approved reference language, not copy its placeholder content literally.

### Required characteristics

- Dark navy / deep blue workspace foundation.
- Cyan/blue NEXORA accent.
- Clear project code and project name.
- Compact client/project identity blocks.
- Progress ring or compact progress indicator with meaningful status.
- Rounded panels with restrained border/glow.
- Stronger content hierarchy than the current white drawer.
- Clear active module state.
- Compact status/priority pills.
- Conversation bubbles with comfortable line length.
- Light mode designed separately, not generated by simply inverting dark colors.
- Motion limited to transform/opacity and short state transitions.
- `prefers-reduced-motion` respected.

### Not allowed

- Giant empty cards.
- Wide blurred backdrop with a narrow workspace in the corner.
- Horizontal module scrolling on standard desktop widths.
- Bright yellow warning fills in Light mode.
- Color-only status communication.
- Excessive glow.
- Long dashboard pages where the primary workspace requires body scroll.

```text
│                       ACTIVE MODULE WORKSPACE                                │
│                                                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 Primary vs secondary modules

Desktop primary navigation:

- Overview
- Execution
- Tickets & Support
- Files
- Client Access

Secondary operations under `More` or contextual actions:

- Linked inquiries / provenance
- Lifecycle / Archive-Restore

This prevents operational/admin-only modules from competing with the daily project workspace.

### 5.3 Workspace height contract

For desktop/tablet landscape:

- Project layer: `100dvh` minus global Admin topbar where applicable.
- Project header + module nav: fixed compact regions.
- Active module: `min-height: 0` and fills remaining space.
- No body-level scroll for Tickets or Files.
- Only module panes scroll internally.

## 6. Admin Header / Project Identity

The current minimal `OPERATIONS / PRJ-001` header is insufficient for the approved direction.

R4 project header must expose, compactly:

- Project code: `PRJ-001`
- Project name: e.g. `darfus_erp`
- Client code: e.g. `CU-003`
- Client display name
- Project status
- Progress percentage
- Target date when available
- Realtime state as a subtle indicator

The header should not include verbose helper/welcome copy. It is an operational header.

## 7. Tickets & Support — Admin

### 7.1 Desktop layout

Target ratio:

- Ticket list: **32–34%**
- Selected ticket/detail: **66–68%**

Both columns must use:

```css
min-width: 0;
min-height: 0;
```

### 7.2 Ticket list

Must contain:

- New Ticket CTA.
- Search.
- Status filter.
- Compact ticket rows.
- Ticket code.
- Title.
- Type.
- Status icon + text + tone.
- Priority icon + text + tone.
- Recency/time.
- Realtime status as a small non-intrusive indicator.

No giant ticket cards.

### 7.3 Ticket detail

Header contains:

- Ticket code.
- Title.
- Status.
- Priority.
- Type.
- Relevant actions.

Conversation area:

- Dedicated local scroll.
- Admin vs Client bubbles visually distinct but within one system.
- Attachments compact inside the message flow.
- Images open in lightbox.
- PDF opens in full preview.
- Audio uses compact player.
- Documents show generic icon + filename + size + download.

Composer:

- Anchored at bottom of detail panel.
- File attachment.
- Text reply.
- Internal/client visibility where Admin policy already supports it.
- No destructive native browser dialogs.

### 7.4 Closed ticket

When status is `closed`:

- Client composer is not rendered/usable.
- Server still rejects client reply.
- Admin sees closed state clearly.
- Any reopen action must follow existing allowed status transition rules; R4 does not invent a new business transition.

## 8. Client Access — Admin Only

This module must become visually obvious and operationally simple.

### 8.1 Empty/no-active-link state

```text
Client Access
────────────────────────────────────────────
Contact        [ Primary client contact ▾ ]
Expires in     [ 90 ] days
Permissions    [ progress ] [ milestones ] [ tasks ] [ tickets ] [ comments ]

                         [ Generate Client Link ]
```

### 8.2 Generated link state

Immediately after generation:

```text
Tracking link
[ https://.../project-portal.html?... ] [ Copy Link ]

Status: Active
Expires: ...
Contact: ...
                                  [ Revoke ]
```

### 8.3 UX requirements

- `Generate Client Link` is the primary CTA.
- `Copy Link` is directly adjacent to the generated URL.
- Copy success uses a small confirmation state/toast.
- Raw token/security metadata is never shown beyond the usable generated URL returned for that creation event.
- Existing active grants appear below as compact rows/cards.
- Revoke uses the existing themed confirmation dialog.
- No `window.confirm` / `prompt`.

### 8.4 Link delivery

R4 does not auto-email or auto-message the client. Admin copies the link and sends it through the desired channel. Automated delivery would be a separate product feature.

## 9. Files — Admin

### 9.1 Desktop layout

Recommended structure:

- Left/RTL-leading navigation rail: **24–30%**
- Main file list/content: **30–36%** when a preview is open
- Preview/detail: remaining **40–46%**

When no file is selected, file list expands into the preview area.

### 9.2 Folder/file navigation

Required:

- Project root.
- Folder tree/list.
- Create folder action.
- File list.
- Upload action.
- Client-visible/internal visibility badge.
- Rename.
- Move.
- Archive/Restore.
- Version metadata where applicable.

Folder creation must use an inline form/drawer/modal, never native `prompt()`.

### 9.3 Preview contract

Image:

```css
object-fit: contain;
max-width: 100%;
max-height: 100%;
```

Never upscale a small raster image to fill a giant panel by default.

PDF:

- Full available preview panel.
- Download action.
- Fallback download if embedded preview cannot render.

Audio:

- Compact native/custom audio controls.
- Range-capable backend behavior retained.

Other documents:

- File icon.
- Name.
- MIME/type.
- Size.
- Download.

## 11. Client Tickets & Support

### Desktop

Same functional ratio as Admin, but calmer visual density:

- List ~34%
- Conversation ~66%

### Own mutations

On successful ticket/message POST:

- Insert/select the returned entity immediately.
- Do not wait for WebSocket echo.
- Do not show a false failure because a later background sync failed.
- Dedupe socket echo by stable ID/request ID.

### New ticket

Desktop: right/side drawer or modal panel.  
Mobile: full-screen form.

On successful creation:

1. Close creation surface immediately.
2. Insert/select ticket immediately.
3. Show ticket workspace.
4. Upload attachments with visible progress/state.
5. Background authoritative refresh may reconcile later.

### Closed ticket

Client sees:

- Lock state.
- Clear message that replies are disabled.
- **New Ticket CTA** immediately available.

## 12. Realtime UX Rules

Existing Durable Object/WebSocket architecture remains protected.

UI rules:

- Own mutation updates local UI immediately.
- Socket events trigger targeted reconciliation.
- No toast spam for every realtime event.
- Live state is a small indicator.
- Reconnect must not destroy typed forms or selected files.
- Realtime refresh must preserve draft text.
- On reconnect, run authoritative resync.
- Background fallback polling is visibility-aware.
- When user is reading older messages, an incoming message must not forcibly scroll to the bottom.
- If user is near bottom, auto-scroll is allowed.
- Otherwise show a compact `New messages` indicator.

## 13. Responsive Architecture

Acceptance widths:

- 1440px
- 1280px
- 1024px
- 768px
- 390px
- 360px

Browser zoom reference: **100%**.

### ≥1280px

- Full horizontal project header.
- Primary modules visible without horizontal scroll.
- Tickets two-column.
- Files multi-column workspace.

### 1024px

- Header metadata compresses.
- Primary modules still directly accessible.
- Tickets remain two-column if usable.
- Files preview may reduce to two regions.

### ≤768px

Switch to mobile/tablet information architecture rather than squeezing desktop.

- Project header becomes compact.
- Module nav may become segmented scroll only if truly necessary.
- Ticket list and ticket detail are separate screens/states.
- Visible Back button in ticket detail.
- New ticket becomes full-screen.
- File list and preview become separate states.

### 390/360px

- No horizontal page overflow.
- Primary CTA fits safely.
- Touch targets ≥44px where practical.
- No two-column forms except tiny paired fields when verified.
- Composer remains visible above mobile browser safe area.

## 14. Dark / Light Theme Contract

### Dark

- Deep navy base.
- Cyan/blue primary.
- Elevated panels distinguished by subtle border/value differences.

### Light

- Near-white/slightly cool base.
- Cyan/blue retained as accent, not as large saturated backgrounds.
- Warning: pale amber background + darker amber text/border.
- Success: pale green + readable darker text.
- Danger: pale red + readable darker text.
- Muted state clearly distinguishable from disabled state.

Every status uses:

- icon
- text
- tone/color

Never color alone.

## 15. Frontend Architecture Decision

R4 should avoid replacing the entire Admin application.

### Recommended structure

Add a dedicated project workspace layer rather than changing the generic drawer globally.

Possible component/module boundaries:

```text
admin/
  project-workspace-shell
    header
    module-nav
    overview
    execution
    tickets
    files
    client-access
    secondary-ops
```

The generic detail drawer remains for Clients, Portfolio Projects, Services, etc.

This minimizes regression risk and preserves accepted modules.

### State rules

Project workspace state should include:

- active project
- active module
- selected ticket
- ticket filters/search
- ticket reply draft
- pending attachments
- selected file/folder
- file upload state
- generated client link state for the current creation event
- realtime connection state

Opening/closing secondary controls must not reset the workspace.

## 18. Acceptance Gates for R4

R4 cannot be accepted by static checks alone.

### Gate A — Static / Regression

- Protected baseline diff exact.
- No migration change.
- No HTTP DELETE.
- JS syntax.
- HTML duplicate IDs.
- AR/EN keys complete.
- No `window.confirm` / native `prompt` in R4 UI path.
- Font Awesome rendering regression protected.
- Primary CTA text remains white where required.

### Gate B — Admin Browser UX

At 1440/1280/1024/768/390/360:

- Full Project Workspace uses available viewport.
- No horizontal clipping.
- Tickets list/detail usable.
- Files list/preview usable.
- Client Access visible without hunting/scrolling modules horizontally on desktop.
- Generate → Copy Link clearly discoverable.
- Light/Dark pass.
- AR/EN pass.

### Gate C — Two-Browser Realtime

Admin + Client Portal simultaneously:

- Client creates ticket → appears in Admin without reload.
- Admin reply → appears in client without reload.
- Client reply → appears in Admin without reload.
- Project progress/status change → client updates without reload.
- No duplicate messages/tickets.
- Draft text survives unrelated socket events/reconnect.

### Gate D — Closed Ticket

- Client composer unavailable when closed.
- Direct client API reply returns rejection.
- New Ticket CTA available.

### Gate E — Private Files

- Client-visible upload.
- Admin receives/observes file without reload where event applies.
- Image preview.
- PDF preview/download.
- Audio/voice note playback.
- Range behavior sufficient for media.
- Rename/move/archive Admin workflow.
- Internal file never exposed to client.

### Gate F — Final No-Regression

- Production counts understood before/after any controlled acceptance writes.
- FK clean.
- Existing public website unaffected.
- Existing Admin routes unaffected.
