# NEXORA — NX-OPS-1.1A Clients Runtime / UX Hardening

## Scope

Runtime/API/Admin hardening over the accepted live baseline:


## 1. Automatic Client Code

Client Code is server-generated and no longer browser-authoritative.

Authoritative rule:

```text
client_number = clients.id
client_code   = "CU-" + client_number padded to a minimum of 3 digits
```

Examples:

```text
id=1     -> CU-001
id=2     -> CU-002
id=1000  -> CU-1000
id=1001  -> CU-1001
```

Three digits are a minimum width, not a cap. The runtime does not use `MAX(client_code)` and does not accept a browser-provided Client Code as authoritative.

Creation is performed as an ordered D1 batch: insert the Client first, then derive `client_code` from the generated row ID. The existing `AUTOINCREMENT` identity remains the sequence authority. Permanent deletion does not reset `sqlite_sequence`, so deleted IDs/codes are not reused.

The same allocator is used by controlled Inquiry -> new Client conversion.

## 2. Client Type / Tax Identifier

The rule is enforced in both Admin UX and Worker validation:

```text
individual -> tax_identifier = NULL
company    -> tax_identifier may be stored
```

For an Individual, the Tax Identifier field is hidden in Admin forms and the server ignores/clears any malicious browser-supplied tax value.

When an existing Company with a Tax Identifier is changed to Individual, Admin receives a themed confirmation before the UI clears the field. The final server rule still guarantees that an Individual cannot retain a Tax Identifier.

The same Company/Individual behavior is present in Inquiry -> Client conversion.

## 3. Lifecycle controls

General profile editing no longer owns Client lifecycle status. Lifecycle is handled through an explicit action endpoint:

```text
POST /api/v1/admin/clients/:id/lifecycle
```

Allowed transitions:

```text
active   --deactivate--> on_hold
active   --archive-----> archived
on_hold  --activate----> active
on_hold  --archive-----> archived
archived --restore-----> active
```

Invalid transitions return a conflict instead of silently rewriting state.

`on_hold` and `archived` Clients cannot be newly linked by operational Inquiry -> existing Client conversion. Reactivation/restoration is required first.

## 4. Guarded permanent delete

Permanent deletion is an explicit owner-approved Admin action:

```text
POST /api/v1/admin/clients/:id/delete
```

There is no generic HTTP `DELETE` route.

Delete requires:

- authenticated Admin;
- same-origin write protection;
- valid CSRF token;
- typing the exact Client Code as confirmation;
- zero protected historical/operational foreign-key relations.

The Worker discovers tables that reference `clients(id)` using SQLite/D1 foreign-key metadata. This makes later relations such as Client Projects, Tickets, or financial records automatic blockers when they exist.

Only these dependency tables are cleanup-eligible:

```text
client_contacts
client_profile_tokens
```

If any other FK relation exists, permanent delete is refused and Admin must use Deactivate or Archive instead. Existing `inquiry_conversions` therefore block deletion.

For an eligible Client the transaction deletes, in order:

```text
client_profile_tokens
client_contacts
clients
```

The action is recorded in the audit log with the deleted Client ID/public ID/code. No sequence reset or code reuse occurs.

## 5. Admin UX

Create Client:

- Client Code is shown as an automatic/read-only hint;
- status is server-owned `active`;
- Tax Identifier appears only for Company;
- existing primary-contact behavior is preserved.

Edit Client:

- Client Code is read-only;
- status is read-only in the profile form;
- lifecycle actions live in a separate section;
- destructive action uses typed Client Code confirmation;
- known Inquiry-linked Clients show deletion as blocked.

Inquiry conversion:

- Client Code input is removed;
- code is generated by the server;
- Tax Identifier is conditional on Company;
- conversion idempotency and Inquiry provenance/status isolation are preserved.

## 6. Themed confirmation / Dark-Light hardening

NX-OPS-1.1A does not use `window.confirm()` for these flows. It adds a reusable NEXORA-themed confirmation dialog with:

- AR/EN text support;
- RTL/LTR compatibility through the existing Admin shell;
- Dark/Light theme styling;
- keyboard Escape handling;
- accessible `role="dialog"` / `aria-modal="true"`;
- dangerous-action styling;
- optional typed-value confirmation.

The accepted select-option Dark/Light fix remains protected and the new lifecycle/read-only/dialog controls include explicit light-mode and responsive styling.

## 7. Security / authority boundary

Every new or changed Client write path retains:

```text
assertSameOrigin
requireAdmin
requireCsrf
```

The browser cannot authoritatively choose:

- Client Code;
- initial Client status;
- lifecycle transitions outside the transition catalog;
- Tax Identifier for an Individual;
- whether a protected Client is permanently deletable.

No Portal access is enabled and `portal_enabled` remains outside this phase.
